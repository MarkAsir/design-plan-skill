# Design Plan Convergence

[中文](README_CN.md)

## Why this skill is needed

Design and implementation-plan documents generated by models are not necessarily complete. Even when OpenSpec or Superpowers is used to produce a structured design or plan, generation does not replace an independent review of current project facts, readiness gates, risks, compatibility, rollback, and verification ownership. Without that review step, important boundaries and dependencies can remain implicit or unverified.

`design-plan-convergence` fills this gap with evidence-driven gate audits, risk-adapted findings, authorized remediation, checkpointed multi-round convergence, and an independent final review.

`design-plan-remediation` confirms the findings identified by `design-plan-convergence` and applies the smallest authorized changes to the affected design or plan documents. `design-plan-convergence-loop` connects audit and remediation into a repeated cycle of audit, confirmation, revision, and re-audit until the findings converge, a decision is required, or the work is correctly routed to a later stage.

An evidence-driven skill set for reviewing and revising design documents and implementation plans through multiple rounds of convergence.

It freezes the current gate, scope, decisions, and evidence boundary before reviewing the documents. When it finds `BLOCKER` or `REQUIRED` issues for the current gate, it repairs only authorized planning artifacts and uses subsequent reviews to verify convergence.

Supported document formats include:

- OpenSpec change artifacts, including proposal, spec, design, and tasks roles.
- Superpowers implementation plans.
- Generic design documents and implementation plans that do not follow a fixed framework.

## Core features

- Multi-round convergence: initial audit → authorized remediation → impact audit → trend analysis → final blind audit.
- Checkpoint and resume: preserves minimal run state across interruption, timeout, or session boundaries; revalidates run identity, gate, boundary, and snapshot before resuming, and starts a new audit generation when they no longer match.
- Explicit gates: supports `DESIGN READY` and `PLAN READY` without automatically entering implementation or release gates.
- Risk profiles: defaults to `AUTO` and also supports `LEAN` and `ASSURANCE`; deeper review is limited to high-risk slices such as security, data, compatibility, concurrency, and rollback.
- Evidence isolation: uses the current snapshot, path state, file hashes, rule snapshots, and external fact revisions instead of treating old reports or remediation claims as current facts.
- Finding routing: distinguishes `BLOCKER`, `REQUIRED`, `CONCERN`, `WATCH`, `NEXT-STAGE NOTE`, `OUT OF SCOPE`, `REJECTED`, and related dispositions.
- Scope control: does not modify implementation, tests, external systems, or frozen upstream decisions. The remediation skill produces only `CANDIDATE CLOSED`; an independent audit confirms final closure.
- Stage-appropriate verification: design review retains behavior, acceptance scenarios, and verification ownership; plan review checks paths, dependencies, ordering, commands, and stable oracles without presenting future execution as completed work.

## The three skills

| Skill                                                                   | Purpose                                                                                          | Can modify documents                  |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------- |
| [`design-plan-convergence`](design-plan-convergence/SKILL.md)           | Run one read-only, risk-adapted gate audit for a design or plan                                  | No                                    |
| [`design-plan-convergence-loop`](design-plan-convergence-loop/SKILL.md) | Orchestrate repeated audit, remediation, and re-audit cycles within an authorized boundary       | Only authorized design/plan documents |
| [`design-plan-remediation`](design-plan-remediation/SKILL.md)           | Apply the smallest root-cause repair to planning artifacts after confirmed current-gate findings | Only authorized design/plan documents |

The usual relationship is: `convergence` finds issues, `remediation` performs authorized repairs, and `convergence-loop` orchestrates the rounds and obtains the final gate decision from an independent audit.

## Usage

### Read-only audit

Use this to determine whether a design is ready for planning or whether an existing plan is ready for execution:

```text
Use $design-plan-convergence to audit openspec/changes/<change-name> at the DESIGN READY gate.
Run a read-only review; change no files. Use the AUTO risk profile and report findings, evidence, and the gate verdict.
```

For an implementation plan:

```text
Use $design-plan-convergence to audit <plan-file> at the PLAN READY gate.
Treat the upstream design as a frozen baseline and check dependency, granularity, risk, coverage, and feasibility.
```

### Multi-round audit and remediation

When you explicitly authorize changes to design or plan documents:

```text
Use $design-plan-convergence-loop to run multiple audit, remediation, and final re-audit rounds for <design-or-plan-path>.
Target the DESIGN READY gate; modify only the specified planning documents, not code, tests, or external systems.
```

The loop stops when:

- The current gate is satisfied and the final snapshot is unchanged.
- User confirmation is required for a product choice, scope, risk acceptance, or write authority.
- The issue belongs to implementation, integration, or release work.
- Remediation stalls, diverges, or introduces an unapproved mechanism.

### Standalone remediation

When an independent audit has already produced findings and you only want to revise authorized planning files:

```text
Use $design-plan-remediation to repair the BLOCKER and REQUIRED findings from the current snapshot in <plan-file>.
Preserve the frozen design and existing structure; make the smallest root-cause repair and return candidate-closure evidence for independent re-audit.
```

`design-plan-remediation` never grants `CLOSED` or `READY` by itself. If a plan issue exposes a design defect, it returns `UPSTREAM DESIGN REOPEN REQUIRED` instead of hiding the defect by changing the plan.

## Review dimensions

The review follows the full chain from evidence to contract, decision, work, verification, delivery, and recovery. It does not stop at formatting or checklist compliance.

### Design review dimensions

| Dimension                  | What it checks                                                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Premise and value          | Whether the problem is evidenced, the value is clear, the observable outcome is defined, and completion can be judged.                                                 |
| Scope and boundaries       | Whether scope, Non-Goals, must-not-change behavior, acceptance boundaries, and hidden scope expansion are controlled.                                                  |
| Architecture and contracts | Whether behavior has clear ownership, decisions and trade-offs are explicit, compatibility and intermediate states are covered, and affected consumers are identified. |
| Delivery and operations    | Whether dependencies, implementation ownership, rollout, risk, rollback or fail-closed behavior, and residual-risk ownership are defined.                              |

### Plan review dimensions

| Dimension   | What it checks                                                                                                                                                                 |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Dependency  | Whether every output exists before it is used, and environments, permissions, owners, and phase ordering are credible.                                                         |
| Granularity | Whether each task has one behavioral result, a stable intermediate state, and a usable verification oracle; tasks are split at behavior, compatibility, or failure boundaries. |
| Risk        | Whether destructive actions, compatibility boundaries, trust boundaries, production activation, rollback, and fail-closed behavior have safe sequencing and ownership.         |
| Coverage    | Whether every approved contract maps to implementation work and verification, and every task traces back to an approved contract.                                              |
| Feasibility | Whether paths, symbols, interfaces, tools, working directories, prerequisites, commands, expected results, and failure interpretation are valid today.                         |

## Gate scope

### DESIGN READY

The design review checks whether the design is sufficient to enter implementation planning:

- Problem, value, scope, Non-Goals, and observable outcome.
- Behavior contracts, acceptance boundaries, rejection classes, and key scenarios.
- Architecture ownership, compatibility, trade-offs, affected consumers, and intermediate states.
- Dependencies, implementation ownership, risks, rollback or fail-closed principles.
- Verification ownership and later-stage routing for each relevant decision chain.

### PLAN READY

The plan review checks whether the implementation plan can be executed reliably:

- Dependencies and phase ordering follow “produce before consume”.
- Tasks are split by behavioral result, compatibility phase, or failure boundary.
- Paths, symbols, interfaces, owners, permissions, working directories, and commands are credible.
- Every approved contract maps to implementation work and verification ownership, and every work item traces back to an approved contract.
- Destructive actions, compatibility boundaries, rollback, and fail-closed ownership are explicit.

Implementation, integration, deployment, release, and full E2E results belong to later gates. Passing a document gate does not execute them automatically.

## Installation

This project is a pure skill document package and has no additional runtime dependencies. Copy all three directories into a skill directory recognized by your runner. Do not install only `convergence-loop`, because the loop depends on the audit and remediation roles.

### Codex on Windows PowerShell

Run this from the repository root:

```powershell
$codexSkills = Join-Path $env:USERPROFILE ".codex\skills"
New-Item -ItemType Directory -Force $codexSkills | Out-Null
Copy-Item -Recurse -Force .\design-plan-convergence, .\design-plan-convergence-loop, .\design-plan-remediation $codexSkills
```

### Codex on Linux/macOS

```bash
mkdir -p ~/.codex/skills
cp -R design-plan-convergence design-plan-convergence-loop design-plan-remediation ~/.codex/skills/
```

Restart or refresh the skill runner, then invoke the skills using the `$design-plan-*` names shown above.

design-plan-remediation/

The `references/` directories contain rules for generic designs, implementation plans, risk gates, evidence snapshots, state orchestration, and remediation admission. The skills select the relevant rules by document type and do not force generic documents into an OpenSpec directory layout.
